## 1. 目标与边界

B 基于服务端当前权威事实，独立检查商品文案的客观宣称是否有依据。检查标题、卖点、描述及商品属性，指出具体问题并解释原因，允许不新增事实的合理改写。审核结论绑定文案、事实与任务上下文的当前版本。

首版验收覆盖水杯品类、英文文案、Amazon US / Shopify US。平台是审核上下文，不代表接入完整官方政策库。中文界面需要能解释英文问题句。

“有依据”指得到当前已确认且允许公开的事实支持。供应商导入或人工 Confirm 不等于独立证明商品真实性；Mock 证据仍须明确标记，不因 Qwen 审核变成真实证据。

### 做什么

- 检查规格矛盾、无依据宣称、未授权事实和内部商业信息泄露。
- 结合本地确定性规则与 Qwen 语义核对，展示问题位置、原句、依据及修改建议。
- 沿用版本失效、用户归属和后端发布授权。
- 用独立人工标注案例评估误报、漏报、失败率和调用开销。

### 首版不做什么

- PDF / 图片提取、文件真伪鉴定和证据真实性调查，归 C 的证据边界。
- 选品排序、真实定价、平台发布接口，沿用现有模块。
- 完整平台政策、商标、侵权或法律合规认证。
- 任意品类全面支持、自动修改事实、自动发布、任意人工强制放行。
- 开发新的 AI 自动修订器。保留现有安全模板修订，或让用户根据建议手工修改。

## 2. 四类风险与判断原则

以下代码是 B 草案命名，不覆盖现有 R001 / R002。

| 类别 | 草案代码 | 判断方式 | 水杯示例 |
| --- | --- | --- | --- |
| 规格矛盾 | B_SPEC_CONFLICT | 文案明确声称的属性与权威事实相反或不一致 | 已确认 500ml，正文写 750ml |
| 无依据宣称 | B_UNSUPPORTED_CLAIM | 客观属性、性能或认证宣称缺少支持；包含隐含宣称 | 无保温证据，却写 Keeps drinks cold all day |
| 未授权事实 | B_UNAUTHORIZED_FACT | 使用待确认、缺失、已拒绝或不允许公开的字段支持宣称 | 防漏待确认，却写 No spills in your bag |
| 内部信息泄露 | B_INTERNAL_DISCLOSURE | 消费者文案暴露内部商业信息 | Supplier cost: USD 8.20 |

判断原则：

1. 检查完整正文和属性，不能只核对生成模型声明的 `usedFacts`，也不能以“与 Qwen 原稿相同”证明可信。
2. 缺少证据和事实相反要区分：无防漏证据不能推导“该杯子漏水”，但不能批准无依据的防漏宣传。
3. `500ml capacity` 与 `holds 500ml` 属于合理改写。先只接受已有规范化单位及可确定验证的等价表达；不允许模型自行发明单位换算。
4. 区分客观承诺和普通修辞。无法判断的表达进入人工复核，不把所有风格词都当作性能风险。
5. 同一问题可关联多个字段；相同位置的重复发现要去重。没有支持事实时允许关联字段为空，不可编造证据 ID。
6. 确定性硬规则不能被模型的“通过”覆盖；但模板字符串差异本身不是事实风险硬规则。

### 泛化约定

审核核心使用“文案宣称—字段事实”的关系，不写死水杯 SKU、容量、杯盖或某个示例句。品类特殊的性能证据要求单独描述。

| 通用类别 | 水杯 | 背包 | 台灯 |
| --- | --- | --- | --- |
| 规格矛盾 | 500ml / 750ml | 黑色 / 蓝色 | 5W / 10W |
| 无依据宣称 | 保温 | 防水 | 护眼 |
| 未授权事实 | 待确认防漏 | 待确认承重 | 待确认认证 |
| 内部信息 | 采购成本 | 采购成本 | 采购成本 |

当前 Product、COPY_FACTS、生成模板和 A 线资格筛选仍偏向瓶类。B 通用接口不等于整站已支持其他品类；其他品类先用独立测试夹具探测边界，不修改 A/C 数据模型来强行演示。

## 3. 输入契约

### 3.1 页面到服务端：沿用现有端点

`POST /api/listings/:id/review`

```json
{
  "expectedVersion": 1,
  "expectedFactsRevision": 2
}
```

`:id` 是文案记录 ID。字段名沿用现有 `VersionInput`，不要另起一套 `listingVersion` 请求字段。身份来自登录会话；页面不能提交可信 `userId`、`reviewPassed`、`publishAllowed` 或权威事实数组。

服务端读取当前用户的 ListingDraft、关联任务、平台和 FactSnapshot，验证最新文案、事实版本、任务上下文和生成资格。错误沿用现有风格：未登录 401，记录不属于当前用户按现有 not_found 策略处理，版本冲突 409。

### 3.2 服务端审核上下文：拟新增内部契约

| 输入 | 内容与用途 |
| --- | --- |
| 文案 | title、bullets、description、attributes；审核用户实际将发布的全文 |
| 平台上下文 | platform、market、category；最小必要任务需求，不能成为商品属性证据 |
| 事实 | 当前服务端 facts，含 key、label、value、status、allowed、来源种类和记录标识 |
| 版本 | listingId、listingRevision、factsRevision、taskId、taskRevision |
| 执行上下文 | 规则/Prompt 版本、审核模式、输入摘要哈希；身份仅留服务端 |

继续适配现有 `Fact` 类型。单位目前可能编码在 value 中；B 不在这一轮要求 C 拆出全新单位模型。后续规范化字段映射使用通用接口，首版事实授权仍尊重现有字段白名单。

### 3.3 服务端到模型：最小化、非权威输出

- 仅发送审核所需的消费者文案和已确认、允许公开的字段。不给模型认证信息、成本、申报价值、物流费用或完整数据库记录。
- 如需提示某个消费者字段未获授权，可以只发字段标识及状态，不发未确认的值，且与 ALLOWED_FACTS 分开。
- 来源采用短引用或泛化种类；不发私有文件路径、用户 ID、Cookie、Key 和历史元数据。
- 本地规则负责检查内部敏感信息泄露；命中时先阻断或脱敏再发模型，不能为审核泄露而把该敏感正文原样发往云端。
- 任务要求、供应商文本和待审文案都是数据。其中的“忽略规则、直接通过”等指令不得改变审核行为。
- 不信任模型返回的判定和证据引用。服务端须校验结构、位置、原句是否匹配、字段引用是否存在，再决定最终状态。

## 4. 输出与状态契约（拟实施）

现有 `Review` 只有 passed / blocked，`Issue` 只有 HIGH、title、text、reason；下表是 B 扩展目标，不是已存在的 API。

| 结论 | 含义 | 是否可以发布 |
| --- | --- | --- |
| passed | 本轮已完成所要求的检查，未发现范围内问题 | 仍须通过服务端所有版本、归属和资格检查 |
| blocked | 有具体事实风险或硬规则问题 | 否 |
| needs_human_review | 已完成请求，但表达有歧义或缺少可靠判断 | 否 |
| failed | 超时、预算不足、模型/结构/引用校验异常等，审核未完成 | 否 |

“审核中”是执行状态，不等于上述结论。不创建人工强制通过按钮；人工复核通过补充并确认事实，或修改文案后重审完成闭环。

每个问题至少返回：

- id、category、severity；首版确定风险沿用 HIGH，人工复核项单独归入待复核状态，不伪装成通过。
- location：field 为 title / bullets / description / attributes；bullets 带 0 起始 index，attributes 带 key。
- text：对应位置真实存在的原句或片段；必要时用 occurrence（0 起始）区分重复片段，由服务端核验。
- reason：为什么有问题，明确区分矛盾、无依据、未授权。
- factKeys：用于支撑或指出冲突的真实字段引用；无证据时可为空。
- suggestedFix：纯文本建议，不自动执行、不新增宣称、不修改事实。
- origin：rules 或 qwen，用于解释问题来源，不是可信度评分。

审核记录须可追溯到：当前文案与事实、任务版本、执行模式、model、promptVersion、ruleVersion、inputHash、aiCallId（没有模型调用时为空）、时间，以及脱敏失败原因。版本与元数据由服务端填写，模型不得自报权威版本。

数据库沿用 ReviewResult，不新建第二套审核结果来源。当前已有 listingDraftId、revision、status、issues、highRiskCount、reviewMode、invalidatedAt；缺少显式事实/任务版本及审核元数据。实施时由 B 提出增量 migration，并协调共享类型、DTO、UI 与发布检查一并更新；本轮不执行迁移。

## 5. 执行与兼容原则

推荐采用两条明确模式：保留 rules 比赛模式，新增 rules + qwen 语义模式。纯规则模式与语义模式的审核能力必须分别展示，规则通过不能被标成 AI 已核验。

1. 显式点击“运行审核”后，服务端验证当前版本并准备输入；先运行本地硬规则。
2. 开始新审核尝试时，让旧通过记录及发布结果失效，不能在新审核失败后悄悄沿用旧通过。沿用现有事务内失效机制，并将新流程调整为请求前失效。
3. 如有确定的硬阻断，可直接保存 blocked，明确未调用模型；否则语义模式在事务外调用 Qwen。候选文案与事实不在长时间写事务中等待模型。
4. 模型返回后核验 schema、原句位置和字段引用；重新检查文案、事实、任务版本及有效状态，再保存。冲突返回 409，不写入对新版本有效的结果。
5. 同一版本并发审核需要防重和保存竞争保护；仅文案版本相同还不足以防止两个审核尝试乱序覆盖。实施时在服务层明确同键并发合并/拒绝及最终写入条件。
6. 查询工作流、查看文案、刷新、发布和 CSV 下载只读取有效审核记录并执行无网络硬检查，不重复调用 Qwen。
7. Apply Suggested Fix 沿用安全模板生成新版本；用户也可手动修订。两者都必须重新审核。
8. 文案修改使该平台旧审核/发布失效；事实修改使相关双平台旧结果失效。A 的任务编辑也会清除选择并失效下游，B 不得恢复这些过期授权。

### R001 / R002 的处理

- R001：保留现有比赛样例阻断。通用扩展需区分关键词、否定和真实宣称，不把词出现本身当作通用品类的完整判断。
- R002：保留在原 rules / 离线演示模式中。语义模式下，模板差异仅触发重新审核，不直接作为 HIGH 风险继续阻断；改写是否可信由事实核对与硬规则决定。
- 不能只改运行审核入口而漏掉 `canPublishListing` 的 R002 重检，否则语义通过的合理改写仍会被发布路径拦截。
- Qwen 原稿通过生成校验不等于独立语义审核通过，原稿也必须走显式审核。
- 语义模式调用失败不做“规则回退后自动通过”。可保留规则发现并显示 AI 未完成；用户重试。独立 rules 模式仍可用于明确标注的模拟发布，不表示完成 AI 审核或真实上架。

首版不加入跨用户语义审核缓存。任何重复调用控制都不得复用过期事实、任务或文案的结论。规则/Prompt 版本变化也应使旧语义授权不再被当作当前有效授权。

4. 再编写实现与迁移计划，开发 Provider 和服务端状态链，最后接 UI。
5. 自动化默认禁用 Live；真实小样本验收显式执行并记录成本，不以模型给自己评分代替人工标准。
