# 人工事实核对与补齐

本轮沿用原五个工作区、`mockApi.ts` 和 localStorage。没有新增后端、数据库或真实业务 API。

## 实际点击路径

### 用内置数据演示，建议先切中文

1. Materials / 商品资料 → **载入内置数据**。
2. 打开 `LM-KT-BTL-005-BLK-500` 的详情，先看“定价已阻断”。
3. 点击 **核对事实 / Review Facts**，进入 Evidence & Facts。此入口允许检查和修复缺资料商品，不会把它直接当成合格推荐。
4. 页面下方 **事实人工核对 / Fact Review** 表格中，找到“包装重量”，状态为 Missing。
5. 点击 **补充值 / Add Value**，输入 `0.42`，单位 kg，点击 **保存数值 / Save Value**。
6. 此时来源为“人工确认”，状态仍是“待确认”，Pricing 继续阻断。
7. 回到该行点击 **确认 / Confirm**。状态变为 Confirmed，Pricing Ready，建议价 **USD 19.20**。
8. 继续“分析证据”。该修复商品的 V2 补充字段先处于待确认；可以确认有把握的字段、拒绝不可信字段，然后生成 Listing。

### 用导入数据演示

导入原样例 XLSX / CSV 后，选择缺重量的 `LM-KT-IMP-005-BLK-500`，按相同步骤确认 `0.42 kg`。此商品采购成本是 USD 7.90，因此建议价是 **USD 18.90**。

两条支线均未使用主角的固定演示价 19.99：

```text
内置缺重量 SKU：8.20 + 3.10 + 0.70 + 2.20 + 5.00 = 19.20
导入缺重量 SKU：7.90 + 3.10 + 0.70 + 2.20 + 5.00 = 18.90
```

包装重量和尺寸是定价前置条件。它们确认后会重新计算快照，但运费仍是固定 Demo 假设，不会根据重量真实查询或调整物流报价。

## 事实状态与文案权限

继续复用 `Fact.status` 和 `Fact.allowed`，没有并行增加另一套 `listingAllowed`。

| 存储状态 | 界面文案 | 正常文案能否使用 |
| --- | --- | --- |
| `Confirmed` | Confirmed / 已确认 | 还必须同时满足 `allowed === true` |
| `Requires Confirmation` | Needs confirmation / 待确认 | 否 |
| `Missing` | Missing / 缺失 | 否 |
| `Rejected` | Rejected / 已拒绝 | 否 |

- 保存新值不会自动确认，先进入 `Requires Confirmation`。
- Confirm 必须有有效值。包装重量和长宽高必须大于 0；容量必须是正整数。采购成本和申报价值允许 0；数值上限为 1000000。
- 可以编辑颜色、容量、材质、原产国、包装重量、长宽高、包装内含、表面工艺、杯盖类型，也支持吸管、采购成本、申报价值。
- 采购成本、申报价值、重量和尺寸即使人工确认，也保持 `allowed: false`，仅用于内部判断。
- `100% leakproof` 性能宣称不能编辑或 Confirm，只能 Reject。Amazon 首次生成保留独立的 Demo risk injection，页面仍明确解释此例外。
- 为保持原主角无需新增点击的主链路，`LM-KT-BTL-001-BLK-500` 的原有 V2 Mock 确认状态保留；其他商品的新 V2 补充字段先为待确认。所有这些状态仍属于演示中的授权流程，不是自动核验了供应商真实性。

## 来源与数据保存

人工修改、确认和拒绝都会记录：

```text
source: Manual confirmation
sourceKind: manual
previousValue: 上次编辑前的值
previousSource: 人工接手前的来源和位置
updatedAt: 本次操作时间
confirmedAt: 确认时间，仅 Confirm 后存在
revision: 当前字段修改次数
```

表格区分 Supplier File、Mock Evidence、Manual Confirmation 三种来源；展开来源可查看位置、原值、原来源和确认时间。

原始供应商目录保留在 `state.catalog`，人工结果按 SKU 保存在 `state.factEdits`。页面、推荐和资料完整度通过 `mockApi.catalog()` / `getCatalog()` 取得有效商品视图；Pricing 和 Listing 从有效事实卡取值。这避免把人工修改伪装成原文件内容。

- **V1** 仍是基础事实卡，现在增加包装长宽高，共 11 个基础字段。明确的人工操作可以更新 V1，随后同步 V2 中继承的基础字段。
- **V2** 仍是增强事实卡。只修改 V2 的杯盖、工艺、包装内容等，不会反写 V1。
- 再次分析证据不会抹掉已保存的人工状态；刷新及重新选择同一 SKU 后仍能恢复。
- Reset、载入内置目录或成功导入新资料集会清除人工修改，恢复相应原始数据。只是切换语言不改变数据。
- 只保存当前人工结果和少量前值元数据，没有引入完整审计日志或版本数据库。

## 下游失效规则

| 事实变化 | 实际行为 |
| --- | --- |
| 包装重量、长宽高、采购成本 | 重新检查确认状态、计算定价；快照版本变化。待确认 / 拒绝时阻断，全部必要字段确认后开放 |
| 颜色、容量、材质 | 旧文案清除；这些必需事实未确认时，禁止生成新文案。定价不受这些字段影响 |
| 杯盖、包装内容、工艺、原产国、吸管等 | 旧文案清除；重新生成时排除未确认 / 已拒绝字段，使用已确认值 |
| 任意人工事实操作 | 清除当前商品 Amazon / Shopify 两个平台的旧 Listing、Review、Publish 结果，必须重新生成并审核 |

这是适合 Demo 的保守策略，没有引入复杂字段依赖图。文案还记录 `factRevision`；发布检查文案版本、事实版本与当前审核是否匹配，避免旧通过状态继续有效。

“核对事实”入口允许检查不完整、重复或类目不符的商品，但不会绕过 SKU 去重和任务类目限制。重复、疑似重复、类目不符的商品仍不能生成文案或发布。

正常文案统一使用 `status === 'Confirmed' && allowed === true` 的事实。修订模板也遵循同一规则：如果杯盖已拒绝，就不会再生成旋拧式杯盖描述；未知或拒绝的吸管事实也不会被默认写成“有吸管”。
